# v0.34.6：从真实执行记录审查科研工作台

本轮保留成果画布、研究内核与现有模型，修复重复处理、等待负担和输出协议问题。当前仍处于单研究者同题实践阶段；工程改进不等于已经证明科研判断优于原工作方式。

## 审查方法与范围

按用户提供的“绿导师视角”框架，采用最小执行轨迹、有状态 Agent、协议与验证、真实目标与指标四个视角。这是框架应用，不代表人物本人对本项目的评价。Ponytail 在本轮落实为复用现有状态与工具、修复最短链路，不增加第二套 Agent 管理或研究数据库。

已审查：材料整理与综合、候选研判和修订、输出合同与引用定位、任务停止和接续、持久化读写、画布阅读和轮询、版本及外部调用边界。依据为实际运行记录的本机只读检查、代码、隔离回归及浏览器操作。没有逐条审定全部文献的科学结论，没有执行新的真实模型评测，也没有把本轮称为全面安全审计。

## 结论与处理

| 发现 | 影响与依据 | 本轮处理 |
|---|---|---|
| 单任务轮询重建整个工作区 | 数百篇材料下，读一项任务也反复解析约250MB全局载荷，再返回约36.7MB任务正文 | 在原SQLite串行队列中按课题、任务读一行；ETag相同返回304，不传重复正文，不重新渲染 |
| 收起的批次仍生成全部文献DOM | 631篇合成界面中，收起区域仍含13,936个后代节点 | 先展开批次，再渲染该批文献；原文按钮和已保存内容保留 |
| 修改报告可能重新逐篇整理相同资料 | 本机已有完整记录，后续修订仍产生重复提取调用 | 仅复用当前报告或明确来路版本的合格记录；重新综合当前问题 |
| 研判未接入已有并发设置 | 界面设置可并行，但该入口仍按默认串行运行 | 接入原有限并发、首错停止派发、在途保存和取消机制 |
| 完整回答因方案字段类型而失败 | 字符串列表与字符串含义可兼容，但原合同仅接收字符串 | 接受两种表示，列表确定性转为项目符号；保留原响应及转换记录 |
| 指定段落中的精确短引文被误拒绝 | 短引文确实存在，但原逻辑强制等于整段 | 接受段内唯一、逐字一致的子串，并记录准确偏移；改写、跨段和歧义仍拒绝 |
| 失败接续可能重发已经完整保存的阶段 | 格式修正后，合格原回答仍可能重复调用 | 用户手动继续时，先本地重新校验相同范围的完整响应；通过才复用 |
| 初判覆盖信息容易被沿用到后续阶段 | 已完整处理后，模型仍可能重复初判“尚未读取”措辞 | 明确传入当前处理范围，阶段分别保存处理量与引用量；旧阶段不被改写 |

## 为什么仍会慢、为什么并非只改JSON

此前串行最高档逐篇提取、输出截断和综合额度问题已在v0.34.4—v0.34.5修复。本轮发现的新开销发生在另一层：重复提取、巨大任务轮询、折叠内容渲染，以及已付出模型成本后的格式失败。

最新本机记录确认：大批领域综合已在用户后续操作中完成，不能继续把旧截图中的未完成状态当作现状。之后的修订与研判仍有独立失败。其中一份旧研判回答在修复字符串列表和精确短引文兼容后，依然有一处引文与实际访问文本不一致；它继续被拒绝。不能删除或改写问题引文，让旧回答看起来已经通过校验。

模型最终综合仍包含很大的上下文，本轮未改变模型、档位、全部材料覆盖或自动压缩其科学内容。页面更轻不代表模型生成同等提速；修复格式也不能证明推荐理由成立。

## 复用、停止与恢复的边界

- 修订复用必须来自选定报告；无自身提取记录的研究分支，只沿已有准确父版本查找。来源缺失、版本不匹配或循环不会转为“取最近一次任务”。
- 同一提供方和模型、相同访问编号、来源、字节文本及访问层级才可复用。原有覆盖与引用验证继续执行；新材料仍需整理。
- 与旧问题相关的“相关性”在新投影中清空，交由本次综合重新判断；原记录保持不变。复用不称为新阅读或新核验。
- 明确要求重新逐篇核对、重读或不要复用时，仍执行重新提取。跨问题自动复用只承接来源事实，不承接旧推荐。
- 已完整返回的阶段，只有在本轮范围相同、未取消、结构与引用均合格时才本地恢复。无正文、部分响应和错误引用不会被补写为成功。
- 沿用原终止状态及写入检查；停止后不再派发新批，在途记录按原规则保留或标记，晚到结果不能覆盖新研究状态。

## 验证证据

**工程回归：403项通过，生产构建通过。** 覆盖跨课题访问、304后状态变化、并发写入后的读取、来源文本变化、父版本断裂、重新逐篇要求、原记录不变、协议类型、引文偏移与错误、有限并发及本地恢复零新调用。首次受限环境的监听测试因EPERM失败，获本机监听权限后全量重跑通过；未修改测试来掩盖失败。

离线数据库副本的三次测量，采用相同任务与数据库，未调用模型：

| 项目 | 原实现 | 新实现 |
|---|---:|---:|
| 读取一个有变化的任务 | 753 / 757 / 757 ms | 96 / 94 / 95 ms |
| 读取未变化任务 | 同原全量路径 | 53 / 53 / 53 ms |
| 未变化时响应正文 | 36,672,489字节 | 0字节 |

这是小样本本机测量，不是端到端模型速度承诺。任务变化时仍会返回其完整记录；全项目首次载入与持久化写入仍有较大成本。

浏览器使用隔离631篇合成材料，桌面1365×1000、手机390×844：收起区域从631篇、13,936个后代节点降至0篇、1个摘要节点；展开一批只渲染25篇。通过原文打开、条件轮询、变化更新、停止保留、无横向溢出与无页面异常检查。没有把页面准备时间作比较，因为两组测试动作和等待不同。

本机真实课题仅只读核查；新代码能够识别可复用的631份旧整理，没有启动它们的模型修订任务。新增真实科研模型调用为0。生产构建仍提示主包较大，尚未进行代码拆分。

部署先确认空闲并备份。首次切换发现既有启动维护新增34条成果版本关联，已自动回退服务并逐行检查：原记录无修改或删除，其余表与模型配置一致；旧版本代码在备份副本上精确重现同样的34条关联。原因确认后再次备份并部署，新旧两次启动之间10张表的内容校验值完全一致，数据库完整性通过。全流程保留原科研记录，未启动模型任务。此处不能概括成“首次部署前后数据完全不变”。

## 后续优化优先级

1. **先评估真实修订输出。** 使用当前研究对象，比较推荐理由、反例与方案取舍，标记具体依据和改变条件。格式成功率、篇数和测试数都不代替研究者评价。
2. **测量综合上下文的重复量。** 后续最值得验证的是重复原文、重复背景和阶段输入膨胀；在完整处理范围不变的前提下，试验按准确材料编号取证与复用。不得把只看部分材料包装成完整处理，也不先重写为Python。
3. **按测量继续缩小持久化边界。** 本轮只改高频任务读取；若首次载入、阶段保存仍成为主要延迟，再增量改相应查询，避免一次重构整个状态系统。
4. **真实案例证明需要后才扩大Agent能力。** 已有Claude Agent SDK试点继续默认关闭。科学执行、更多工具与通用Agent平台没有因本轮修复而自动获得权限。

下一步应在研究者原有工作中验证“改一次判断不再重跑全部提取，失败后保留可读成果”，再比较科学质量；不以增加模块或自动采纳结论作为升级完成标准。

## 复用的标准机制

条件读取采用标准[HTTP条件请求](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Conditional_requests)；按需显示采用[React条件渲染](https://react.dev/learn/conditional-rendering)。现有SQLite、任务记录、引用与版本继续作为权威来源，没有引入新的运行依赖或数据迁移。
