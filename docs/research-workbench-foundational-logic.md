# 科研工作台底层逻辑基准 v1.0

> 最本质的定义：帮助研究者把当前的模糊与困惑，逐步转化为自己理解、自己选择、能够继续执行的研究工作；工作台负责辅助过程，不替研究者拥有最终决定权。

本文件集中保存截至 2026-09-03 已确认的产品原则、科研流程与逻辑编排，作为以后设计、开发和恢复工作的首读基准。不是重新审查方案，也不是新增需求。

## 1. 基准状态与适用顺序

- 基本框架、模块化结构、步骤目的及已确认的科研逻辑修正，作为当前稳定基准，不因换会话、换模型或开始开发而重新提问。
- 架构选定为脚本＋Agent。此处“已确定”指设计与编排方向，不等于全部功能、接口、连接器和代码已经实现或通过验收。
- 用户已要求暂停完整前端设计；本轮只归档，不修改产品代码，不做全流程成本验证。
- 本文件整合最新决定。若旧模块、旧审查、执行表或现有代码与之冲突，应用本文件中的更正，不静默恢复旧规则。
- 后续只有用户明确改变决定，或新事实形成必须处理的具体冲突时，才讨论对应差异；不重启整套框架审查。工程实现细化不应变成对既定步骤目的的重复确认。

阅读优先级：用户后续明确决定 → 本基准及其决定来源 → 不冲突的科研运行规范 → 既有模块与执行表细节 → 历史提案和实现参考。来源、访问层级、执行事实与不确定性始终如实表达。

## 2. 产品本体与责任边界

### 2.1 泛领域方法，生物医学起步

工作台的方法主线是从当前研究需求出发，逐渐明确研究问题、研究路线与具体方法，再衔接真实执行和成果表达。生物医学是创建者熟悉的起点与首个验证场景，不是产品永久的学科边界。PubMed 等数据库是资料连接器，不是工作台本体。

“泛领域核心”是架构与方法定位，不表示已经接入所有学科数据库、具备各领域专业能力或完成跨领域效果验证。第一版先做共用核心功能，不按学历或职业身份拆产品，也不因此承诺首版做全所有科研功能。

### 2.2 工作台、用户和真实执行者

| 主体 | 负责什么 | 不能被混淆为什么 |
|---|---|---|
| 用户／研究者 | 表达目标、理解结果、比较与取舍、决定题目和方案、掌握最终研究判断 | 被工作台考核或审批的下属 |
| 工作台与 Agent | 整理资料、解释当前区域和步骤、生成候选方案、答疑、提示未知与风险、辅助推进 | 科学裁判、用户上级、真实实验的替身 |
| 已接入的数字工具 | 在具体授权和能力范围内真实运行，并返回可核对的结果 | 仅生成计划就宣称已执行 |
| 研究者、实验室或相应机构 | 实际实验、招募、干预、样本采集、真人专业审查和机构决定 | 由模型模拟意见即可替代的执行者 |

工作台可以指出矛盾、信息缺口和风险，解释后果并建议核查；不能以“系统科学通过／不通过”、总可信度分数或模型多数票替用户裁决研究成立与否。技术上不可运行、没有授权或缺少真实输入时，说明具体限制，不把限制包装成对科研价值的否决。

AI 复核与真人审查通过统一声明区分，不在每条建议后重复免责声明。具体记录仍如实注明来源与实际执行者；只有用户当下需要处理的具体风险才就地提示。统一声明不是外部操作授权。

## 3. 保留既有模块与研究主线

既有九阶段主旅程和 M00—M14 共 15 个模块作为结构来源保留；不重新拆分步骤，不新增一套平行科研流程。下表是按最新决定解释既有阶段，不是新增关卡，也不把一个阶段中的多个步骤合并成自动运行区间。

| 既有研究阶段 | 已有目的 | 主要交付 |
|---|---|---|
| 研究意图与现实条件 | 明白用户目前要解决什么、已有工作和可用条件 | 当前目标、现实条件与待澄清点 |
| 领域认识 | 帮助用户理解概念、研究现状、分歧和可探索方向 | 有来源与访问边界的领域简报 |
| 选题形成与收敛 | 解释候选问题的差异，让用户逐步明确自己的题目 | 候选比较、用户选择与当前研究问题 |
| 研究路线与方案设计 | 将问题对应到成果形式、研究设计、技术与资源 | 具体方案、方法选择依据和未定项 |
| 问题相关的资料与证据 | 组织实际读到的资料，说明支持、分歧和缺口 | 关联文献、证据记录与使用边界 |
| 方案与成果表达准备 | 将用户采用的方案及所需大纲、图表计划等整理清楚 | 当前方案版本与适用的执行／表达计划 |
| 真实执行、分析与结果整理 | 衔接实际研究，记录发生了什么，并解释结果 | 真实执行记录、分析结果、偏离与局限 |
| 核心正文写作 | 忠实于研究记录和证据，将已有工作写清楚 | 可追溯的章节与正文修订 |
| 全文收束与可选投稿 | 完成整体表达、核查与指定成果交付 | 指定版本成果；用户需要时准备投稿材料 |

源模块中“合同”“冻结”“终审”等旧词不得解释为工作台拥有科学批准权。“当前采用的方案版本”不等于永久不可修改；检查完成不等于科学成立；准备投稿材料不等于已获对外提交授权。

这些阶段是研究路径，不是所有用户必须依次完成的清单。可按当前问题迭代、局部返回，也可以停在领域简报、题目比较、研究方案、结果解释或稿件，不自动升级目标。

完整结构与来源：[模块化规划基线及 15 个模块](../outputs/research-workbench-modular-v1.0-2026-09-02/科研工作台模块化规划基线-v1.0.md)。完整能力目录：[全面执行表 v1.0](../outputs/research-workbench-execution-matrix-v1.0-2026-09-03/EXECUTION-MATRIX.md)，共 104 项任务，每项 9 列；这些任务不等于 104 次用户确认、104 个页面或 104 个常驻 Agent。

## 4. 每个研究步骤的交互原则

### 4.1 交流内容已经由步骤目的确定

除逐段正文写作的明确例外，**每个研究步骤都与用户交互**：

1. 展示并解释这一步的结果，让用户明白当前区域在做什么、结果意味着什么。
2. 回答用户围绕结果提出的问题，帮助解除困惑。
3. 承接用户的偏好、修改或继续意图，按已有流程引导后续研究。

不重新设计一套“每一步究竟要交流什么”的问卷。既有步骤与目的提供交流范围；本步的实际结果和用户的问题提供交流内容。

用户可以没有疑问并直接继续，不需要填写统一字数的理由、通过理解考试或接受系统的科学结论。也不能只在系统认为存在重大取舍或权限变化时才交流，然后静默越过其他研究步骤。

### 4.2 三种行为必须区分

| 行为 | 适用方式 |
|---|---|
| 研究步骤交互 | 解释本步结果、答疑、承接反馈，是正常研究过程 |
| 步骤内后台执行 | 保存、格式处理、分页取回、范围内工具处理和安全重试，不新增用户关卡 |
| 外部操作授权 | 数据去向、用途、接收方、动作范围或费用承诺等需要具体许可时，按授权规则处理 |

减少重复授权和技术确认，不等于取消研究步骤交互。保留交互，也不等于每条后台任务都必须暂停。

### 4.3 正文写作的明确例外

在用户给定的写作任务、范围和已有依据内，正文可以逐段连续写，不必每段暂停询问。这个例外不包括自动选题、自动采纳研究方法、开展现实实验、越过其他研究步骤或自动投稿。

### 4.4 结果阅读与答疑的当前方向

用户已初步认可“原文保留在阅读区，引用内容带入问答区”的并排示意。其用途是让用户看得见自己在问哪段话，并在理解过程中保留上下文；答疑本身不等于要求修改原文。

这只是当前可接受的交互方向，不是完整前端设计定稿。布局尺寸、视觉风格、组件细节和移动端表达留待以后设计，不纳入不可变的底层逻辑。演示使用预设内容，未接入模型。

## 5. 按已有研究进度接入

- 模糊需求可从意图和领域认识开始；已有题目可直接进入相关调研、证据整理或方法设计。
- 已有方案、数据、大纲或稿件，按其实际完成程度和本次目标接续，不强制重走选题。
- 用户决定从哪里继续，工作台解释并建议；所选任务缺必要信息时局部补问，不要求补齐无关旧表单。
- 沿用用户已有工作，不冒充工作台执行过被跳过的步骤；材料存在、已读取和已核查必须区分。

## 6. 脚本＋Agent 的底层编排

总原则：**程序负责可靠执行，Agent 负责理解与探索，用户负责研究决定。**

- 脚本指可测试的确定性应用代码、任务处理器和工具适配器，负责调度、调用、状态记录、格式、保存、版本与恢复，不仅指命令行脚本。
- 模型与 Agent 负责需要语言理解、比较、解释、规划或探索的任务；不因需要智能就把所有任务改成 Agent 自由行动。
- 各步骤使用适合其任务的工具与产物，并沿用同一研究上下文；后续步骤接续前一步的结果与用户反馈，而不是把研究变成彼此割裂的聊天。
- 研究流程的推进受当前用户目标、已有产物、反馈、可用工具和具体授权约束，不自动运行完整科研链条。
- 架构选择不要求每个模块都有独立常驻身份，不要求 Agent 间自由聊天总线，也不把模型数量当作质量或科学正确性的证明。

全面执行表已经给出纯脚本、单次模型、有界 Agent、有限并行、工作单、产物交接及恢复等实现建议。具体字段、通信机制、模型选择、并行策略和重试参数仍属工程细化，不冒充用户逐项确认或真实运行验收；但细化时必须遵守本文件已确定的研究与交互原则。

执行表部分旧行只写“用户决定触发”，没有完整表达每步正常交互。后续将其同步到本节与第 4 节，是文档／实现映射工作，不是再次询问用户要不要逐步交流或重新划分步骤目的。旧“只在重要取舍才问”的自动推进建议不再有效。

## 7. 材料、版本与恢复

### 7.1 Zotero 与工作台的分工

文献资料优先在 Zotero 中管理和阅读，工作台关联资料并支持当前研究任务，不另造一套复杂文献管理器。不同资料组／版本使用集合、子集合及可读名称表达范围与版本限制。

集合名称不是不可变内容快照，集合不是独立条目副本，资料版本也不是整个研究项目的版本。这个决定不授权全库同步、所有研究资产迁入、自动外发或修改 Zotero 内容；不宣称集成已经实现。

### 7.2 方案自动保存与逐版本导出

方案自动保存为线性历史，每个已保存版本都可手动导出；不做复杂版本分支，不额外要求手动保存、另存或命名里程碑。

导出所选版本当时的真实内容，不误导出最新版本，不在导出时调用模型重写；导出不改变当前使用版本。未被采纳的 AI 建议不静默替换用户当前方案。若沿用恢复操作，恢复旧内容后形成新的线性记录，不覆盖或删除中间历史；不做版本分支也不意味着取消候选选题比较。

自动保存服务于连续工作和恢复，不冒充无限备份或 Zotero 全库快照。具体保存频率、文件格式及工程恢复策略不是本轮新增决定。

## 8. 授权、用量与成本

外部操作按需、限定范围授权；用户明确允许记住的项目、资料、工具／接收方、用途和动作范围内，不反复询问。范围扩大或用途、接收方变化时再确认；覆盖、发布、发给他人或超出既有许可的额外付费操作保留预览与确认。

授权可查看和撤销后续使用，拒绝仅影响相应操作。读取不自动扩展为上传、回写或外发，统一声明也不替代具体操作许可。

项目目前没有商业化，预计接入其他 AI 模型 API；API 产生多少费用，按实际服务产生的费用理解，不预设工作台套餐、积分、订阅层级或平台加价。普通已授权计量调用不逐次弹出付费确认。

实际费用以服务商计费事实为准；仅有用量、估算或未知时如实区分，不把估算写成已结算金额。此处未选定供应商、模型、费率、预算界面，不授权无限调用；本轮没有接入 API 或开展全流程成本验证。

## 9. 科研诚实性与直接简报

以下要求继续适用，是对系统表达与执行的约束，不是赋予工作台科学裁决权：

- 领域扫描、候选发现和大范围筛选默认以题名与摘要为主；全文不是摘要级任务完成的前提。
- 每条来源注明实际访问层级。摘要没报告的内容记为“摘要未报告”或“未知”，不能补造，也不能写成“没有实施”。
- 用户明确要求全文核查，或任务需要精确方法、数值、强因果主张、正式写作及全文审计时，按需要核查少量关键全文，不默认全库通读。
- 计划不是执行，草案不是结果；区分模型建议、真实数字运行、研究者记录、真人审查与机构决定。
- 科研推进的最终回复直接给用户可独立阅读的简报：当前时期、本轮结论、依据与边界、下一步或待用户决定；不只交文件，不用内部阶段代码代替自然语言。

完整运行依据：[科研 Harness 运行规范 v1.2](research-harness-canonical-runtime-v1.2-2026-08-10.md)。其中历史“冻结／批准”措辞按本文件的人类决定权与任务范围解释，不恢复全局科学门槛。

## 10. 明确保留的设计 Badcase

| 不再推进的方向 | 为什么不这么做 | 已确认替代原则 |
|---|---|---|
| 工作台判断研究是否科学，并据此批准或阻断 | 将辅助工具变成研究者的上级，替代用户最终决定 | 展示依据、未知、分歧与建议，由用户判断 |
| 只在重大取舍时问用户，跨研究步骤连续生成 | 把减少重复权限确认误当作取消用户理解与参与 | 每步解释结果、答疑并承接反馈；正文逐段写作例外 |
| 把医学起点当成永久领域边界 | 把当前资料源与案例误当成产品方法本体 | 泛领域方法核心，生物医学起步验证 |
| 重复问既定步骤目的、强制理由或重走已有流程 | 增加负担，不能帮助当前研究更清楚 | 复用已有进度和决定，只处理本次任务真实缺口 |
| 每条建议重复统一声明，或每次计量调用都弹窗 | 把透明和授权变成持续噪声 | 统一声明＋具体风险提示；限定范围授权 |
| 用模型计划、文件夹名称或流程状态代替真实事实 | 混淆方案、版本标签与实际执行和证据 | 如实记录实际内容、访问层级、执行者与版本 |

原始否决记录：[科学裁判 Badcase](../design-checkpoints/2026-09-02-research-workbench-human-agency-principle/01-badcase-scientific-arbiter.md)、[跨步骤自动推进的更正](../design-checkpoints/2026-09-02-research-workbench-human-agency-principle/12-decision-step-interaction-and-api-cost.md)。保留这些记录是为了避免以后以“优化”为名重新引入，并非待办修复提案。

## 11. 后续如何使用这份文档

1. 先读本文件恢复原则和边界，再看[当前断点](../design-checkpoints/CURRENT-RESEARCH-WORKBENCH.md)。
2. 只按后续具体任务读取执行表和对应来源模块；不重复全框架审查，不把旧提案覆盖最新决定。
3. 产品优化先与用户讨论；完整前端设计等用户开启。本次示意不等于视觉规范或产品代码。
4. 工程工作按用户后续授权的范围实现和验证；明确“已确认逻辑”“待同步文档”“待实现”“已验证”，不混为一谈。
5. 只有实质新信息或明确变更才更新基准，记录改变了什么、为什么变、更晚决定来自哪里；不静默覆盖历史。
