# 科研工作台测试交互日志：网络药理学

> Test ID：NP-UX-TEST-001｜状态：进行中｜用途：下一版本产品迭代｜开始日期：2026-08-09

## 记录边界

本日志保存用户可见的人机交互、系统对需求的解释、产物版本变化和可执行的产品洞察。不保存模型隐藏推理、密钥、个人敏感数据或与测试无关的完整上下文。用户原话优先保留；若后续需要对外分享，应先去标识化并取得用户确认。

## 测试目标

验证科研工作台能否把模糊研究主题转化为：容易理解的约 1000 字阶段简报、可展开的结构化 Agent 产物、明确的人类决策点，以及能够继续进入下一阶段的研究方案。

## 关键交互事件

### 事件 1：模糊主题输入

- 用户原话：`网络网络药理学发展现状`
- 系统理解：将重复的“网络”视为笔误；用户需要快速进入领域，而不是立即得到确定性综述结论。
- 可见产物：G0 用户简报 v1。
- 产品发现：短主题输入默认应触发“导师式入门 + 研究范围界定”，而不是生成一篇泛泛长报告。

### 事件 2：抽象标签和内容不足

- 用户原话：`你这个图片展示得不够具体。什么叫做2021-2026年是规范，规范了什么，你需要为你的图加一个图注。并且你给我的文字不够完整。你要作为一个博士生导师带领研究生快速入门，为我讲述领域重点以及侧重点变化，并且你的语言要更加具体，但是总字数不变。`
- 系统修改：解释“规范”涉及数据来源与筛选、节点和边、参数与版本、不确定性、验证及数据代码开放；增加图注；压缩低价值叙述以保持阅读量。
- 可见产物：G0 用户简报 v2。
- 产品发现：时间节点不能只写“规范化、智能化、转化”等抽象词，必须同时回答“规范什么、改变了什么、边界是什么”。

### 事件 3：术语门槛和图形密度

- 用户原话：`什么叫做bottom-up、top-down和middle-out三种路线。你的语言要用我能看得懂的，或者说普适性的语言。你这图片的信息有了，但是同一个阶段的信息不希望全部挤进一个代码块，而是核心时间变化，其余信息以树干发散。`
- 系统修改：把三条路线翻译为“从药物出发、从疾病出发、两边会合”；增加修机器类比、适用场景与风险；把时间变化设为主干，重点、方法和问题拆成分支。
- 可见产物：G0 用户简报 v3。
- 产品发现：默认用户层应先出现普通语言，专业术语作为第二层标签；复杂时间图应采用“主干 + 分支”，避免单节点塞入完整段落。

### 事件 4：阶段批准与测试声明

- 用户原话：`是。ps：你记住现在是测试，保留我们的人机交互，作为下个版本迭代参考。`
- 系统理解：批准以 middle-out 为推荐路线进入 G1；建立持久化交互日志。
- 可见产物：G1 检索方案简报。
- Agent 产物：G1 StagePack、检索式、纳排标准、筛选和提取结构。
- 产品发现：一句“是”可以完成 Gate，但界面应回显“系统理解为批准什么”，避免多选项场景中的误批准。

## 下一版本可执行改进

1. 用户首次输入主题后，先自动判断“快速入门、选题、综述还是实验设计”，并在简报顶部显示当前任务模式。
2. 用户层默认显示普通语言；专业术语提供括号、悬浮解释或展开卡，不让术语阻断主线阅读。
3. 时间图采用固定模板：中央主干只放年份与核心转折，分支放研究重点、典型方法和遗留问题，每幅图强制生成图注。
4. 1000 字简报与 Agent StagePack 必须由同一对象状态渲染，修订简报时同步更新术语和图形映射，避免双重真相。
5. Gate 按钮或自然语言批准后，显示一句“已批准：研究主线／范围／下一阶段”，并允许立即撤回或修改。
6. 将“需要用户追问后才解释的内容”记录为首屏缺陷，作为下一版本的核心质量指标。

## 后续继续记录

每次测试新增一条事件：用户原话、系统理解、可见产物、Agent 产物、用户是否接受、暴露的问题和下一版修改建议。正式研究证据另存于 StagePack，不与产品测试观察混写。

### 事件 5：暂停科研流程，先做产品 Review

- 用户原话：`你先对于产品做一个review沉淀下来`
- 系统理解：暂停 G1 实际检索，先复盘本轮从模糊主题到阶段批准的产品表现。
- 沉淀产物：`docs/research-workbench-product-review-network-pharmacology-test-v1-2026-08-09.md`。
- 核心结论：价值主张通过；首次理解、批准回显、双层产物一致性和阶段语义尚未通过。
- 产品发现：工作台必须允许用户随时进入“复盘当前流程”的元层，而不丢失科研阶段状态。

### 事件 6：恢复 G1 科研流程

- 用户原话：`不用，进入g1`
- 系统理解：不制作 MVP v2.1，保留 Review，恢复 G1 证据侦察并实际运行检索校准。
- 用户可见产物：`network-pharmacology-g1-evidence-recon-brief-v2-2026-08-09.md`。
- Agent 产物：检索运行计数、31条题名摘要试筛、哨兵召回与路线判定规则。
- 产品发现：元层 Review 不应强制打断科研主任务；用户拒绝产品改版后，应能从原阶段无损恢复。

### 事件 7：用户授权阶段内自主完成

- 用户原话：`这一部分你自己做完，直到可以回报的时候，返回我简报`
- 系统理解：用户授权在既定 G1 范围内自主完成检索收敛、全文试提取、反证核查和产物冻结；不授权越过 G1 自动批准研究结论或进入 G2。
- 用户可见产物：只返回约 1000 字 G1 最终简报和一幅带图注的领域演进图。
- Agent 产物：冻结检索方案、Claim–Evidence–Counterevidence 矩阵、证据分级、路线判定规则和不可变 StagePack。
- 证据纠错：G0 v2 曾将指南概括为要求“数据代码开放”；G1 核对原文后改为“报告数据来源、版本、日期、参数、软件和验证，使过程可追溯”。指南原文未被解释为一律强制公开原始数据与代码，旧表述不得继承到后续阶段。
- 产品发现：阶段内可以设置“安静运行直到 Gate”的交互模式，但结束时必须说明完成范围、证据边界和唯一待决策事项；后台全面不等于前台堆叠产物。

### 事件 8：G1 的用途和工具不够具体

- 用户原话：`g1主要解决了什么，我可以拿g1做什么。你所说的内容不够具体，比如工具具体是什么，不要说具体步骤，但是起码告诉大家一些更具体的`
- 系统理解：用户并非索要操作教程，而是需要知道 G1 减少了哪些研究不确定性、各研究对象对应哪些真实工具、工具会产生什么以及不能证明什么。
- 用户可见修改：新增“四个已解决问题”“七类具体工具地图”“五种可直接用途”。
- Agent 产物修改：科研证据状态不变，只新增用户投影 v2 和 StagePack v4；避免为了改善解释而重新生成事实层。
- 产品发现：阶段简报必须同时回答“本阶段替我做了什么、我能拿它做什么、下一步会用到什么”，否则用户只看到知识总结，看不到工作台的阶段价值。

### 事件 9：用户要求检索可复现并引入渐进式研究契约

- 用户原话：`并且你也没有告诉我检索式，我无法复现你的内容。你遵守这个内容，不要在意他具体的含义，比如第一集等等。严格遵守这个不断明确的过程研究思路，再结合我们现在的agent现状。`
- 参考文件：`local-reference/AI综述论文陪跑训练营-提示词工作台.html`。
- 系统纠错：旧扩展检索只保存概念摘要，未保存完整字符串，不能精确复现；Scopus/CNKI 未执行。G1 总状态由“完成”重开为“部分完成、不可作为发表级综述”。
- 用户可见修改：新增已运行 PubMed 检索式、候选 Scopus/CNKI 检索式、计数、运行状态和复现字段。
- Agent 流程修改：固定采用“主题澄清—实体化—语义群—检索矩阵—真实执行—前100条反馈—文献库冻结—领域分析—证据大纲—段落写作—独立核查”的递进关系。
- 产品发现：搜索结果数量不是完成标志；只有检索式、运行日志、噪声反馈、漏检校准和文献库快照共同存在时，系统才可以显示“可复现”。

### 事件 10：用户追问 PubMed 搜索究竟能得出什么

- 用户原话：`完成下一步，你这一步pubmed搜索能得出什么结论吗`
- 系统理解：用户要的不是继续堆检索数量，而是完成摘要层校准，并明确区分“PubMed 已支持的判断”与“尚不能下的结论”。
- 实际完成：复核修订式 51 条题名中的 19 条方法/平台候选摘要；识别 1 组重复版本记录；将数据库/算法敏感性、计算可复现与生物学验证的区别、平台自动化与方法比较的不平衡固化为探索性结论。
- 边界纠错：17,528 条母集不能解释为 17,528 项高质量研究；题名/摘要检索不能直接量化 bottom-up、middle-out、top-down 的年度占比；对接或分子动力学稳定性不能自动升级为靶点参与或临床有效证据。
- 外部阻塞：Scopus 高级检索页面在两个浏览器入口均超时；CNKI 高级检索出现证书域名错误，系统未绕过安全警告。故 PubMed 分支完成校准，但正式 G1 仍未冻结。
- 产品发现：每次 SearchRun 的用户界面必须同时展示“命中量、有效校准样本、允许结论、禁止结论”；只有命中量会诱导用户把检索规模误当成证据强度。

### 事件 11：用户要求继续完成 G1

- 用户原话：`继续完成g1`
- 系统动作：通过 NCBI 官方接口重新取得修订方法式的全部 51 条 PMID 和元数据，建立稳定记录编号、筛选状态与版本家族；冻结为 51 条记录、50 个研究家族的 PubMed 方法学候选库，并保存 SHA-256。
- 去重发现：PMID 33173863（预印本）与 PMID 35057621（期刊版）属于同一工作流研究；保留两条来源记录以保存 lineage，分析计数只算一个研究家族。
- 跨库状态：Scopus 访问被导向 Elsevier 登录页；CNKI 高级检索被导向滑块验证码。系统未绕过登录、验证码或安全策略，亦未把失败访问解释成零命中。
- 用户交互：前台只展示一个恢复动作——完成 Scopus 登录和 CNKI 验证；不要求用户阅读 51 条后台记录或重新提供检索式。
- 产品发现：外部数据库登录属于可恢复的 Human Handoff，不应让整个 Run 失败；系统必须保存 checkpoint、打开待处理页面，并在恢复后从相同 SearchProtocol 继续。

### 事件 12：用户批准忽略 Scopus 与 CNKI

- 用户原话：`忽略这两个`，随后确认 `先继续进行`。
- 系统理解：这是对当前 G1 数据库范围的明确修改授权，而不是将未执行检索伪装为完成；当前范围正式改为 `PubMed-only methodological orientation`。
- 完成动作：以已冻结的 51 条记录、50 个研究家族作为方法学候选库，生成最终用户简报、范围声明和带图注的路线变化图；StagePack v8 将 G1 标记为 scoped complete，并允许带范围限制进入 G2。
- 结论限制：不得在后续阶段声称跨语种穷尽、精确年度路线占比或发表级系统综述完成；若目标升级，必须重新打开 G1 补做跨库检索。
- 产品发现：用户应能主动缩小证据范围以降低门槛，但产品必须把“范围内完成”和“普遍完成”分开显示；缩小范围应生成新的 Decision 和 StagePack，而不是覆盖原始失败记录。

### 事件 13：用户要求继续并完成 G2

- 用户原话：`继续，你作为顶级的科研人员，完成g2`
- 系统理解：在已批准的 `PubMed-only methodological orientation` 内完成 G2 方案成形及独立核查；“完成”指把可签署的科学内容包做完，不代替用户作最终 G2 人工批准，也不自动开始正式筛选。
- 权威输入：以 `NP-G1-20260810-v8` 和 `NP-G1-LIB-002` 为当前状态；旧 `CAL-003` 与 completion checkpoint 作为用户忽略 Scopus/CNKI 前的历史快照保留，不再阻塞 G2。
- 关键方法修订：初稿只富集高证据信号会产生 spectrum bias，故改为 M 方法证据全量识别 + A 应用研究分层随机审计；A 从 17,528 条 PubMed 母集计划抽取 700 个研究家族，E/O/C 仅作非互斥组件与案例补充，不进入实践分母。
- 关键证据修订：把 E3 拆为 E3a 结合/细胞占有与 E3b 靶点特异功能介导；完整靶点因果还需浓度/暴露相容。PMID 39669203 因暴露与表型跨物种而降为 E4 待全文对齐，PMID 31619994 的具体靶点因果保持未定。
- 检索校准：2026-08-10 通过 NCBI E-utilities 实跑候选式，A=17,528、M=183、M2=15、E=911、O=2,329、C=2,455、H=108；所有计数重叠、含语义噪声且不是纳入证据，正式检索仍需 PRESS、query translation、哨兵召回与末次检索日冻结。
- 统计冻结：预设 Hájek 域比例、Taylor 线性化方差、有限总体修正、design-based 95% CI、时期绝对差及缺失结局界限；名义样本的 ±7/±10 个百分点不再被当作最终精度。
- 独立核查：独立 Agent Methodologist 和 Evidence Auditor 的初审均要求实质修订；关闭全部必改项后，两者最终均为 `PASS`。Agent 核查不替代人工 PI、PRESS 或双人筛选/抽取。
- G2 产物：Protocol v1、Evidence-driven Outline v1、PilotChartingSchema v1、Independent Review v1、用户简报 v1 和 StagePack v1；StagePack SHA-256 为 `43c237d064d2cf909760aa75961e9fdedcc17ec66b5a11b10473245e06cddbf8`。
- 当前状态：`G2_content_package_complete=true`，`human_G2_approval=pending`，`formal_G2_complete=false`，`G3_allowed=false`，正式执行继续受人工决定、PRESS、注册、双人校准和 Charting 试填阻塞。
- 产品发现：阶段“科研内容完成”和“人工 Gate 已批准”必须拆成两个可见状态；独立审查的初始失败、修订闭环和最终结论应成为正式对象，而不是只留在聊天记录中。

### 事件 14：用户纠正简报交付方式

- 用户原话：`用户简报是你直接返回给我的`
- 系统纠错：上一轮只给出“G2 用户简报”文件链接，没有把简报正文直接呈现在回复中；这违背双层交付中“用户层直接可读、Agent 层按需展开”的原则。
- 立即修正：在当前回复中直接返回完整 G2 用户简报；Protocol、StagePack、Evidence Outline、Charting Schema 和审查记录继续作为后台文件链接。
- 产品发现：每个阶段结束时，用户简报必须成为主回复本体，不能要求用户点击文件才能获得阶段结论；文件链接只能作为可追溯的第二层证据与结构化对象。

### 事件 15：用户要求回到科研叙事并严格遵循训练营流程

- 用户原话：`你这些文字的表述给我一种看技术报告的感觉……我不想知道G1、G2、G3……我只想知道目前什么时期……你要严格地遵守我发给你的那个科研的流程。`
- 系统核对：重新读取 `local-reference/AI综述论文陪跑训练营-提示词工作台.html`，确认流程依次为领域分析、精准文献重检索与前100条反馈优化、逐篇A/B/C/D信息提炼、依据文献数量生成大纲、文献分类、分段写作和事实核查。
- 阶段纠错：当前应显示为“文献调研第二阶段——精准文献重检索与策略优化”，而不是面向用户显示 G2；现有 Protocol 仅是后台检索与质量控制草案，不能冒充已经完成的领域综述或数据驱动大纲。
- 表达纠错：用户层删除 `strict middle-out`、E3a/E3b、StagePack、Gate、Schema 等内部术语；必要概念改写为“从药物出发”“从疾病出发”“让药物暴露、具体靶点和表型变化形成可检验的证据链”。
- 内容纠错：阶段报告必须先回答领域目前形成了什么认识、最重要的问题是什么、哪些判断有证据、哪些尚不能下结论；检索命中量、字段和统计设计降到后台，不能代替科研结论。
- 流程约束：在完成最终主题的矩阵式检索、前100条相关性反馈和文献库冻结之前，不进入逐篇信息提炼；在完成A/B/C/D提炼和子主题文献计数之前，不生成正式论文大纲；在大纲和文献映射完成之前，不进入正文写作。

### 事件 29：完成摘要优先的证据大纲与独立结构核查

- 当前时期：进入`论证结构形成`，不是继续扩大全文获取，也不是开始撰写综述正文。
- 大纲主线：用五个连续问题组织证据——为什么预测必须复核、成分是否真实到达、成分是否作用于具体靶点、药效是否依赖该靶点且证据是否对齐、现有证据允许写到什么程度。
- 证据映射：13篇应用研究全部映射到具体章节，并逐节记录唯一论文数、PMID、访问层级、允许结论、反证与限制、禁止外推以及证据不足时的合并或降级规则；数据库稳定性只调用4项已核查方法来源，和13篇应用研究分开计数。
- 结构收缩：不按疾病、方剂或实验技术逐篇堆叠；人工智能、多组学、单细胞、定量系统药理学、技术路线比例和年度趋势均因当前证据不足而不设独立章节。
- 独立核查：由未生成大纲初稿的代理完成全文压力测试并通过；单篇未知主题已降为案例框，所有0篇或未建立结论都限定为“本轮可访问材料”。该通过只表示证据与结构一致，不构成人类研究者批准。
- 当前决定：证据大纲内容和独立核查已经完成，暂停在`确认论文论证路线`；在研究者确认前，不自动写论文正文。

### 事件 30：研究者退回概念性大纲，要求改成可直接写作的论文大纲

- 用户原话：`你给出来的大纲也不是清晰可以直接用于论文写作的大纲啊，更像是这个领域的特点概述，不是真正用于论文写作的大纲。`

### 事件 31：完成可直接写作的段落级论文大纲与独立复核

- 当前时期：仍处于`论文论证结构形成`，本次完成的是可直接用于逐段写作的论文路线，不是论文正文。
- 文章定位：固定为`PubMed限定、基于定向证据语料的聚焦批判性方法综述与证据地图`；不称系统综述或正式范围综述，也不声称遵循 PRISMA-ScR。
- 写作骨架：按结构化摘要、引言、方法、结果、讨论和结论组织为43个拟写段落；每段均明确可直接使用的主题句、证据出现顺序、必须保留的限定句、段末过渡、图表位置和建议字数。
